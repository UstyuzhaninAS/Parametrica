Три системные проблемы

01

Срывы сроков

Долгое формирование исполнительной документации и альбомов разных разделов. Расчет ТЭП — группа не всегда успевает корректно сформировать BIM-модель для автоматической подгрузки данных. Ручной пересчет = 4-8 часов на проект.

Автоматизация + AI

Автоматическое формирование альбомов из BIM. AI-ассистент проверки комплектности и ТЭП. Сокращение времени с дней до часов.

02

Зоопарк коммуникаций

Синхронизация между подразделениями через почту, мессенджеры. Задачи теряются, статусы не видны. Нет единого источника истины.

Шаблоны Outlook + AI-агенты

Шаблоны писем при отправке заданий и результатов. AI считывает шаблоны → автоматически размещает данные в Kaiten, Google Таблицах, ЭЛМА. Сроки, ответственные, KPI — всё в одном месте.

03

Отсутствие нормоконтроля

Нет отдела ПТО. Заказчик давит за качество. Ошибки в штампах, коллизии, несоответствия нормам. Возвраты документации — 3-4 итерации до утверждения.

Revit-экспорт + AI-нормоконтроль

Revit-модель экспортирует XML/IFC/PDF → AI-агенты считывают, определяют ошибки, коллизии, несоответствия федеральным/муниципальным нормам и замечаниям в базе (Фонд реновации, ДГП, заказчик).

Локальные модели 72B+

Задача Модель Обоснование
Основная логика, RAG, анализ договоров, юридические риски Qwen2.5-72B-Instruct Лучшая открытая модель для русского языка. Превосходит Llama-3-70B в логике и работе с длинным контекстом (до 128k токенов).
Генерация кода (Python, Dynamo, C# для Revit API) Qwen2.5-Coder-32B-Instruct (или 72B) Специализированная кодовая модель. 32B версия работает быстро и превосходит крупные модели в написании и отладке скриптов.
Анализ графики, PDF-альбомов, чертежей (VLM) Qwen2-VL-72B-Instruct или Llama-3.2-90B-Vision Мультимодальные модели, способные «смотреть» на изображения, схемы, фрагменты чертежей и отвечать на вопросы по ним.
Векторизация (Embeddings) для RAG-базы BGE-m3 или multilingual-e5-large Не требуют больших GPU. Специализированы для создания векторных представлений текстов на множестве языков, включая русский.
OCR (Распознавание сканов) PaddleOCR или Surya Специализированные легкие нейросети. Использовать 70B модель для OCR неэффективно и дорого.

Почему 72B, а не 32B: юридическая точность, нормоконтроль с длинными СП, мультимодальность для чертежей, прогнозирование на больших исторических данных — всё это требует моделей уровня 70B+.

Почему не коробочный СОД

Проблема «Бульдозера для картошки»

Рынок СОД (Pilot-BIM, Vitro-CAD) ориентирован на Заказчика/Девелопера и Генподрядчика. Функции стройконтроля, фото360, порталы подрядчиков, управление поставками составляют до 60% стоимости и функционала. Для проектного бюро это мертвый груз.

Реальность Государственной Экспертизы

Формально требования к BIM-модели существуют. Но в РФ (2026) отсутствует полноценное отечественное ПО для замены Revit. Экспертиза принимает документацию преимущественно в PDF/DWG. Жесткие требования к OpenBIM на практике отсутствуют.

Кто должен платить?

Если Заказчику нужен полный СОД — это его зона ответственности и его бюджет. Он должен купить СОД и «затаскивать» в него всех участников. Покупать СОД своими силами, чтобы уговаривать Заказчика — стратегическая ошибка.

6 реальных потребностей Генпроектировщика

Если отсечь «строительный» и «заказчицкий» функционал, реально необходимые функции СОД для проектного бюро:

  • Версионность файлов (RVT, IFC, PDF, DWG) с историей изменений
  • Система замечаний (Issue Tracking), привязанная к листам или элементам модели
  • Внутренние маршруты согласования (до выпуска Заказчику)
  • Централизованный архив проектов и единое пространство данных
  • Авто-Ведомости выдачи документов
  • Интеграция с ЭЛМА (связь технических файлов с договорами и счетами)

Именно эти 6 функций дают 90% прироста эффективности бюро. Остальные 30 функций из стандартного списка СОД нам не нужны.

Кто должен платить за СОД

Полный СОД нужен заказчику для контроля стройки и управления подрядчиками — именно он должен быть инициатором, это его зона ответственности и его бюджет.

Разделение ответственности:

  • Заказчик покупает — полный СОД для управления стройкой, подрядчиками, исполнительной документацией
  • Заказчик предоставляет — портал/доступ всем участникам: проектировщикам, генподрядчикам, субподрядчикам
  • Мы обеспечиваем — выдачу данных в требуемых форматах (IFC, PDF, DWG) через наш «Легкий СОД»

Только при условии работы всеми участниками в единой цифровой среде, технологии BIM «взлетят» и дадут качественно иной уровень в работе строителя.

🚀 AI-движок обработки замечаний проверяющих органов

Проблема

Сотни Word-файлов (10 КБ – 5 МБ) в месяц от МФР, ДГП, экспертизы. Вручную: извлечение шифров, осей, фрагментов изображений, текста замечания и автора занимает дни. Высокий риск пропустить критичное замечание или не заметить, что оно уже устранено в актуальной версии.

Технический стек

  • Парсинг: python-docx (извлечение текста, таблиц, изображений, метаданных)
  • OCR: PaddleOCR (распознавание текста на фрагментах чертежей)
  • Логика и классификация: Qwen2.5-72B-Instruct (типизация, извлечение сущностей: раздел, ссылка на СП, критичность)
  • Проверка легитимности (VLM): Qwen2-VL-72B (сравнение фрагмента из замечания с актуальным чертежом, загруженным с сервера по шифру)
  • RAG и БД: BGE-m3 + Qdrant + PostgreSQL (векторизация, поиск исторических паттернов)

Пайплайн обработки (6 этапов)

1. Парсинг Word: извлечение текста, осей, шифра, автора, изображений
2. OCR: распознавание текста на фрагментах чертежей
3. Структурирование (72B): типизация (пожарка/конструктив), оценка критичности
4. Проверка легитимности (VL-72B): сравнение фрагмента с актуальной моделью на сервере
5. RAG + БД: сохранение, поиск похожих замечаний в истории
6. Паттерны + рассылка: генерация сводных писем ГИПам и чек-листов МФР/ДГП

Реализуемость на DGX Spark

Да, реализуемо. 128 ГБ унифицированной памяти DGX Spark достаточно.

  • Вариант А (1 DGX Spark): Последовательная обработка. Модели подгружаются по очереди. Пропускная способность: ~1-2 минуты на файл. Для сотен файлов в месяц достаточно пакетной обработки (ночью/в фоне).
  • Вариант Б (2 DGX Spark, рекомендуется): Параллельная обработка. Один узел держит Qwen2.5-72B (логика, RAG), второй выделен под Qwen2-VL-72B (анализ изображений). Максимальная скорость и качество.

Затраты и сроки

  • Срок: ~24 недели (6 месяцев) поэтапной разработки
  • Стоимость разработки: ~2 150 000 ₽ (ФОТ команды: frontend, backend, AI-инженер)
  • Железо: +600 000 ₽ (за 2-й DGX Spark для параллельной работы, опционально)

Эффект

  • Сокращение времени обработки замечаний с дней до часов
  • Автоматическое формирование чек-листов проверяющих органов на основе выявленных паттернов
  • Снижение количества возвратов документации за счет предварительной AI-проверки легитимности

Проблема

Технический стек

  • Backend: Python FastAPI + PostgreSQL + pgvector (для RAG)
  • AI-модели: Qwen2.5-72B-Instruct (логика) + BGE-m3 (embeddings) + Qwen2-VL-72B (анализ сканов)
  • Интеграции: 1С:Договоры, ЭЛМА, Контур.Проверка/СПАРК, судебная практика (RAG)

Интерфейс пользователя

1. ПРЕДМЕТ ДОГОВОРА — Наименование товара/услуги ✓
2. СТОИМОСТЬ И ОПЛАТА — Цена, НДС, аванс ✓
3. СРОКИ ПОСТАВКИ — Требует уточнения ⚠
4. ОТВЕТСТВЕННОСТЬ — Неустойка 0.5%/день (риск!) ✗
5. РАЗРЕШЕНИЕ СПОРОВ — Опционально ○

Как работает AI-агент

  • Анализирует тип договора (поставка, услуги, подряд, аренда) → автоматически подгружает нужные ветки дерева

  • Проверяет риски: красным — юридические риски (несоответствие ГК РФ), желтым — нестандартные условия, зеленым — типовые безопасные формулировки
  • RAG по базе договоров: поиск похожих договоров в компании, предложение формулировок из успешных контрактов
  • Анализ истории разногласий с контрагентом
  • Генерация полного текста договора по выбранным пунктам

Затраты и сроки

  • Срок: 19 недель (4-5 месяцев)
  • Стоимость: ~2 050 000 ₽
  • Команда: 1 frontend + 1 backend + 1 AI-инженер

Эффект

  • Сокращение времени подготовки договора с 3-5 дней до 2-3 часов
  • Снижение юридических рисков на 60-70%
  • Стандартизация договорной базы
  • Экономия ~150-200 часов юристов в месяц

Технический стек

  • Frontend: React + TypeScript + Ant Design
  • Backend: Python FastAPI + PostgreSQL
  • AI-модели: Qwen2.5-72B-Instruct (логика) + BGE-m3 (RAG по предыдущим ТЗ)
  • Интеграции: Revit API (автоизвлечение ТЭП), Kaiten (задачи смежникам)

Интерфейс пользователя

4. СОСТАВ ДОКУМЕНТАЦИИ — АР, КЖ, ИОС ✓

  • Команда: 1 frontend + 1 backend + 1 AI-инженер (частично)

Эффект

  • Сокращение времени составления ТЗ с 4-6 часов до 30-40 минут
  • Стандартизация ТЗ по компании
  • Снижение количества уточнений от смежников на 50%

✉️ Конструктор ответов на замечания

Проблема

Ручное составление таблиц ответов на замечания ГГЭ/МГЭ занимает 2-3 дня. Часто забывают ответить на часть замечаний, формулировки несогласованны.

Технический стек

  • Frontend: React + TypeScript + Ant Design
  • Backend: Python FastAPI + PostgreSQL
  • AI-модели: Qwen2.5-72B-Instruct (генерация ответов) + PaddleOCR (распознавание PDF замечаний) + BGE-m3 (RAG по базе успешных ответов)
  • Интеграции: Экспорт в Excel/Word, ЭЛМА (маршрутизация на согласование)

Интерфейс пользователя

Замечание №1 (АР) — Принято, исправлено ✓
Замечание №2 (КЖ) — Частично принято, требуется уточнение ⚠
Замечание №3 (ИОС) — Не принято, обоснование ✗
Замечание №4 (АР) — Ожидает ответа ○

Как работает AI-агент

  • Загрузка PDF с замечаниями → OCR (PaddleOCR) → извлечение текста
  • AI группирует замечания по разделам (АР, КЖ, ИОС)
  • RAG по базе успешных ответов → предложение формулировок из похожих проектов
  • AI генерирует черновик ответа для каждого замечания
  • Юрист/ГИП проверяет и утверждает (Human in the loop)
  • Автоматическая генерация итоговой таблицы в Excel/Word
  • Проверка полноты ответов (AI сверяет с требованиями экспертизы)

Затраты и сроки

  • Срок: 6 недель (1.5 месяца)
  • Стоимость: ~600 000 ₽
  • Команда: 1 frontend + 1 backend + 1 AI-инженер (частично)

Эффект

  • Сокращение времени подготовки ответов с 2-3 дней до 2-3 часов
  • Снижение количества возвратов от экспертизы на 40-50%
  • Стандартизация формулировок ответов
